## 4. 合并、选用、审核和放行（看到全量输出之前写定）

`merge_full.py` 的规则：

1. **来源核对**：
   - 试点的 `gate.json` 必须已放行，清单哈希等于它的 `bound_to`；
   - 其余阶段的协议检查必须 `pass`，清单哈希等于 report 里记的值；
   - 所有阶段的划分清单哈希相同。
2. **跨阶段去重**：顺序是 pilot → main → supp1 → supp2，后面的对和前面任一阶段的对相同（任一方向）就去掉，已放行的试点样本优先，不会被静默替换。
3. **直接父样本**：按 `batch_id` 和过滤前的位置（`pair_uid` 的序号 = Rk 的 k − 1）回填 `direct_parent_family_id`、`direct_parent_sample_id`、`ref_index`、`stage`，并核对生成标签等于父样本标签。试点也这样回填，不按过滤后的行号对齐。
4. **隔离**：每一行的 `usable_folds` 必须等于批内所有上下文家族签名的交集，而且包含在直接父家族的签名里。补充批次也只放同一签名、同一组的家族，所以不需要"挪配额到超集签名"。主轮按实际库存派发，空格子产出为零；缺口只由补充轮按逐折四类缺口补，不跨类补。
5. **逐折选用**（`fold_selection.csv`：fold、sample_id、pair_uid）：
   - 每折每类的需求是该折 fit 的行数。
   - 候选按阶段顺序排，阶段内用固定种子（20261106、折号、组）打乱，依次取整对，同一对的方向一起选，直到行数恰好等于需求。
   - E 对 2 行 E；单向对 1 行 F + 1 行 B；O 对 1 行 O。
   - 五折分别核对 E / F / B / O 的精确行数，供给不够就 `fold_quota` 失败。
   - `usable_folds` 只表示资格；某一折实际用哪些行，只看 `fold_selection.csv`。
6. **自动检查**：合并后的全部候选按冻结的停止条件重算（失败批次、重复、探针、词数）；新增部分另算一份，只描述。
7. **第二次 P1**：
   - 总体：新增的（非试点）、过滤后、至少被一折选用的对，每个 `pair_uid` 只算一次，包括补充轮。
   - 每个生成标签抽 20 对，种子 20261107，展示方向随机，隐藏生成标签和父样本。
   - 两人独立标注，用 `process_outputs.py score` 计分，门槛不变。
   - 报告样本覆盖的签名、主轮 / 补充来源。60 对不代表覆盖所有小格子。
   - 候选清单或逐折选用改了，审核失效。
8. **集中度**（`concentration.json`）：按直接父家族报告派发数、保留数、选用数，独立家族数、最大值，以及子对数最多的前 1% 家族的占比（前 1% = ceil(0.01 × 有子对的家族数) 个家族）。同一对的方向算一对。
9. **放行**：`gate.json` 绑定 `manifest.csv`、`fold_selection.csv`、`sources.json`（各阶段包、清单、report、日志的哈希和两个种子）、`review_sheet.csv`、`review_key.json`、`report.json`。协议、失败批次、重复、探针、词数、逐折配额、第二次 P1 全部 `pass` 才放行。
10. **失败时**：合并后的自动检查或第二次 P1 不通过，就不训练、报告结果。不做 v7 调参（11-05 的约定）。

## 8. 协议修订 1（11-06，主轮检查点之后）

**起因**：主轮第一次额度中断后续跑时，`main_b002`、`main_b082` 的第二次尝试漏传了冻结提示词末尾的一个换行符。日志同时记了实际哈希和期望哈希。Claude 独立复算：实际哈希恰好等于"冻结提示词去掉末尾一个换行符"的哈希，其余字节完全相同。两批的回复都格式合格。冻结的 `process_outputs.py` 会因此判整个主轮协议失败。

**修订**（`augb-protocol-r1`）：
- 记录的 `prompt_sha256` 等于"冻结提示词去掉末尾一个换行符"的哈希，而且日志写明 `expected_prompt_sha256` 等于批次文件的值：记为 `prompt_deviations`，单独列出，不算协议失败。
- 其他任何不一致仍是协议失败。
- 过滤、停止条件、审核和放行都不变。

**理由**：
- 模型收到的指令和冻结版本只差一个行尾符，语义上没有差别。
- 作废两批合格输出、或者结束整轮，代价都远大于这处偏差的影响。
- 修订只针对这一种可以精确复算的差异，不放宽其他核对。
- 做这个决定时，Claude 没有看任何生成内容。Claude 还是第二次 P1 的审核人，所以也不该看。

**已验证**：
- 新增测试：只差换行符且写明期望哈希的通过；没写期望哈希、或者不只差换行符的仍然失败。
- 在真实检查点上运行：除了未派发的 115 批，没有其他协议问题，偏差恰好是这两次。

**一并如实记录**：
- `main_b042`、`main_b082` 的第一次尝试只有预定的生成器 ID，无法确认是否派发成功。`main_b002` 的第一次有实际 ID，但没有可恢复的输出。三批都按一次基础设施中断计。
- 所有批次（包括试点）日志里的提示词哈希，都是调度方对要发送文本算的，不是对实际传输消息的独立回读。`main_b042` 的第二次尝试也是这样。第 2 节第 4 条的派发前核对能缩小这个缺口，但不能消除。

## 10. 改用 Haiku 5.5 单一来源（11-06，Pan-Yan-0 定的；在看到任何 Haiku 输出之前写定）

**决定**：生成器改为 Claude Haiku 5.5 子 agent，由 Claude 调度，**单一来源，全部重来**。GPT 调度生成的数据（v4–v6 试点、主轮已交回的 6 批）只留档，不进 +1。

这样做也绕开了第 9 节"实际模型说不清"的问题。

**调度方式**：
- 每批开一个全新的子 agent（Claude 的 Agent 工具，`model: haiku`，无历史继承），模型在调用参数里显式指定。日志的 `requested_model` 记 `claude-haiku-5-5`（调用参数 `haiku`）。
- 提示词不经 Claude 转抄：Claude 把批次文件里的 `prompt` 原样写成 `prompts/<batch_id>.txt`，核对哈希等于 `prompt_sha256`。
- 子 agent 收到一段固定的派发说明：读这个文件，照它的要求作答；除这个文件外不打开任何文件、不上网；把回复原样写进 `outputs/<batch_id>/attempt_N.txt`，只回复 done。
- 日志的 `prompt_sha256` 记提示词文件的哈希；派发说明的模板另记 `dispatch_wrapper_sha256`。
- 回复也不经 Claude 转抄：`attempt_N.txt` 由子 agent 自己写，Claude 只算哈希、跑格式检查。
- 尝试上限和格式重试的规则不变：每批最多 1 次基础设施重派、1 次格式重试。

**smoke**：
- 用 v6 的 15 个试点批次，父样本和提示词都不变。
- 用冻结的 `process_outputs.py build` 判定：协议、失败批次、重复、探针差距、词数偏离，全部 `pass` 才跑主轮 121 批；任何一条不过就停下报告，不调提示词。
- smoke 的 15 批计入 Haiku 数据，在合并里占试点的位置。

**审核**：
- Claude 是派发方，不做 P1 审核人，按"生成方不做主审核"的原则。
- P1 只在全部 Haiku 数据合并、逐折选用之后做一次：总体是全部被选用的 Haiku 对，每类 20 对；审核人是 Pan-Yan-0 和 GPT；门槛不变。
- 不通过就不训练、报告结果。
- `merge_full.py` 现在要求试点阶段已经过 P1。Haiku 的试点阶段只有自动检查，合并代码要相应改，在跑合并之前改好并测试。

**已知风险**：
- 子 agent 有读文件的工具，派发说明禁止读其他文件，但技术上不能强制，和 GPT 的子 agent 一样。
- 子 agent 是否会带上本仓库的 CLAUDE.md / AGENTS.md 作为上下文，不确定。AGENTS.md 里有从训练标签归纳的计数规则描述，提示词本身已经禁止只差数量的对。
- Haiku 比 Luna 小，质量要看 smoke 和最后的 P1。

**实现**：
- `haiku_dispatch.py`：`prep` 写提示词文件并核对哈希；`wrapper` 打印派发说明（模板 `690dd6c4…`）；`record` 算回复哈希、跑格式检查、追加日志（`source: claude-haiku-5-5`、`requested_model: haiku`）。
- `process_outputs.py`：manifest 的 `source` 取日志里的 `source`（GPT 的旧日志没有这个字段，仍记 luna），`generator_model` 记 `requested_model`。
- `merge_full.py --pilot-unreviewed`：试点按其他阶段核对，另外要求它的自动检查全部通过；第二次 P1 的总体包括试点阶段。

**结果**（[metrics/augment_b/haiku_full](../../metrics/augment_b/haiku_full/README.md)）：
- smoke：15 批第一次就合格，210 对全部保留，词数偏离 0.6%，探针 +2.8 pp，全部通过，所以按规则跑了主轮。
- 主轮：121 批第一次就合格，保留 1,478 / 1,489 对，词数偏离 0.2%，探针 +2.2 pp。
- 补充第 1 轮：按实际缺口规划 9 批（224 行，预算上限 586），全部合格；之后每折四类都补满，不需要第 2 轮。
- 合并：145 批、1,805 对、选用 1,794 对；重复 1.0%；126 个家族用了 2 次。
- 子 agent 每次带约 10 万 token 的初始上下文，只调用 3–4 次工具；初始上下文的内容无法证明。
- P1 审核表 60 对（试点 7、主轮 50、补充 3），答案封存 `57f50c0f…`。

**P1 的协议偏离（11-06，在打开答案之前定下）**：
- 原定 Pan-Yan-0 和 GPT 各自独立标注。实际做法是 GPT 先标一遍，Pan-Yan-0 再在它的基础上审核修改，交回一份标注（SHA-256 `a2bf3d85…`），所以两份不独立。
- Pan-Yan-0 选定按一份共识标注计分（协议 `P1C`）：去掉 U 之后，和生成标签不同的比例每类不超过 30%、可判定项不少于 10 个才算 pass，三类都 pass 才放行。
- 和原 P1 的区别：原 P1 只看两人一致的项，两人分歧的项会被剔除；P1C 没有可剔除的分歧项，每个确定标签都计入，所以不比原规则宽松。
- 代码：`process_outputs.py score <输出目录> P1C <共识标注.csv>`。`gate.json` 只在 `sources.json` 记了 `pilot_reviewed: false`（Haiku 合并）时接受 P1C，其他合并仍只认 P1。
- 报告里写明：这一次人工审核是 GPT 和 Pan-Yan-0 的共识判断，不是两人独立判断，审核人之间的一致率无从得知。

**P1 结果**：E 19 项可判定、9 项不一致（47%，fail）；单向 18 项、4 项（22%，pass）；O 18 项、0 项（pass）。`gate.json` 的 review 为 fail，不放行。分析和可选的下一步见 [haiku_full README](../../metrics/augment_b/haiku_full/README.md)。
