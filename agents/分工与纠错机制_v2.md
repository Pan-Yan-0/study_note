## 2. Google Drive 主工作区与 GitHub 同步架构

**核心原则（Pan-Yan-0 已定）**：以 **Google Drive（`Pan-Yan-0_工作区`）作为所有端共同读写的主工作区**，**GitHub 保存同步副本、运行 Actions 补充复核并保留版本历史**。

| 内容类别 | Google Drive（所有端共同读写主工作区） | GitHub（同步副本、Actions 复核与版本历史） |
|---|---|---|
| **分工、各线状态、学习存档** | 当前权威版本，各端从这里开工 | 同步到对应公开（`study_note`）或私有仓库（`personal_study_image`） |
| **NLP 论文、素材、图片、音频、视频** | 原文件和正式产物统一保存 | 保存需要版本管理的文字、索引和引用 |
| **SemEval 代码、配置、运行包** | 保存对应版本，供各端读取和交接 | 同版本代码用于 `diff`、测试和 Actions |
| **权重、逐条预测、结果 ZIP** | 完整保存，附 `SHA-256` 哈希 | 保存指标摘要、清单和哈希 |
| **审阅意见、自动检查回执** | 写回对应任务目录，所有端可读 | 保存运行记录与必要的审计证据 |

### 2.1 可见范围隔离与文件管理 6 项必要信息

1. **Drive 内两级可见状态与发布前拦截位置**：
   - **`工作区私有`（默认）**：所有新草稿、私有记录、个人画像、中间讨论默认处于该状态，只留在 Drive 私有工作区或同步至私有仓库。
   - **`允许公开发布`**：拟从 Drive 导出进入公开仓库 `study_note` 的笔记、实验文档与代码，**必须在本地 `git commit / git push` 之前**（而非等到 push 后才靠 Actions 事后报错）通过 `agents/check_repo_hygiene.py` 硬门禁与对应内容审阅：从 Drive 导出单文件核验时运行 `--files <导出文件> --require-public-ready --require-task-scope --verify-receipt <回执JSON>`（同步确保该任务已被列入仓库 `agents/current_task.json` 的 `active_tasks` 中）；在本地推仓前由 `pre-push` 钩子自动拦截全部拟推送 commit；GitHub Actions 在 push/PR 后运行 `--ownership-mode error --require-task-scope --require-public-ready --check-task-pool` 做补充复核，标记为 `允许公开发布` 且状态为 `通过` 后方可合入。
2. **交接与任务文件固定记录 6 项必要信息**（由 `agents/check_repo_hygiene.py --require-handoff-header` 自动校验）：
   - `任务与当前负责人`（如 `TASK-LEARN-001 | Gemini 网页端`）
   - `允许修改范围`（如 `ML_note/原理笔记/`、`ML_note/实验/ShortGPT_BI删层/`）
   - `来源版本`（记录源 Git commit、Drive `fileId` 与输入内容 `SHA-256`）
   - `可见范围`（`工作区私有` 或 `允许公开发布`）
   - `当前状态`（`待提稿` / `待审` / `退回` / `通过`）
   - `正式结果链接`（及拟合入仓库的 `目标仓库路径`；正式文件原位更新保留同一链接，旧交接稿移入归档目录，统一入口只指向当前版本；更新 Drive 副本前核对源 commit 与内容哈希，避免两边各自修改后互相覆盖）。

### 2.2 互通与防覆盖的五步闭环同步

1. **统一入口读取与方向边界下发**：各端先从 Drive 的统一入口（`00_入口/当前任务与交接入口.md`）读取当前任务的大致方向与四条硬边界（目标、允许修改范围、数据源、公开/私有红线）；具体实现方式随 `Pan-Yan-0` 在各端实操反馈动态调优。
2. **确定版本送检**：Antigravity 基建把 Drive 上的确定版本拉取到本地检查，记录 **Drive 文件 ID、实际字节 `SHA-256` 哈希和基线 Git commit** 的对应关系；学习线同时联动运行 `check_repo_hygiene.py` 与 `check_archive.py`。
3. **版本绑定回执写回 Drive 与发布前校验**：
   - 自动检查生成的回执（`CHECK_RECEIPT_<任务ID>.md` 与 `.json`）写回 Drive 对应任务目录，同时记录双检查器结果与被检文件的实际字节 `SHA-256`。
   - **明确区分“格式检查通过”与“内容审阅通过”**：处于 `工作区私有` / `待审` 状态的交接稿，回执显式标注“仅代表格式/隐私/任务范围检查通过；内容待审，尚未获准公开发布”。
   - 若写作者在检查期间又改了文件，或校验时未传入待审文件的实际字节（空输入），`--verify-receipt` 直接报错拦截。
4. **任务级分端信息共享池（消除跨端“已发给某端但未推 GitHub/Drive”的信息盲区）**：
   - 信息共享池**按“每个任务 × 每个端”分立维护**（不混成全体大杂烩），在 Drive `00_入口/当前任务与交接入口.md` 第 1.1 节、对应工作线 `10_交接/<工作线>/POOL_<TASK-ID>.md` 以及公开仓库 [`agents/task_pools/<TASK-ID>.json`](task_pools/) 登记每个活跃任务在 **`Pan-Yan-0` 本地/平台、`GPT / Codex 端`、`Antigravity 端`、`Gemini 网页端`、`Google Drive 主工作区`、`GitHub 仓库`** 的文件持有状态、版本号 / `SHA-256` 及**未共享待同步项**。
   - 当 `Pan-Yan-0` 已把正式回传包或材料发给某一端（如已发给 GPT/Codex），但该端尚未 `git add -f` 推上 GitHub 或尚未同步至 Drive `20_实验包/<TASK-ID>/` 时，池内显式标为 `信息未共享（某端已持有，待同步至 GitHub/Drive）`，避免另一端误判为“尚未生成”或盲目报错；`check_repo_hygiene.py --check-task-pool` 自动校验 `agents/task_pools/*.json` 与任务清单的一致性及 `github_repo: "synced"` 产物的仓库跟踪完整性（拦截只交 `README.md` 而漏交 `.gitignore` 忽略的数据文件的假同步）。
5. **交付前独立子 agent 自审查门禁（防 C-006 同类事实与路径错误）**：
   - 凡向 `Pan-Yan-0` 或其他端交付**跨端启动提示、任务入口变更、交接包或复算结论**前，起草端（如 Antigravity 基建或 SemEval 对话）**不得仅靠主上下文凭记忆直接输出**，必须先派生至少 1 个**只读独立审查子 agent（Reviewer / Challenger / Explorer）**，逐字核对：① 仓库最新 commit 中的实验组名/臂名与指标表头、② 冻结计划与 README 原文协议条件、③ 仓库与 Drive 实际存在的文件路径及 `SHA-256`、④ `agents/current_task.json` 允许与禁止修改范围。独立子 agent 审查通过并留存记录后方可交付。

### 3.1 把“任务允许改哪里”与“公开发布门禁”接入自动检查

1. **活跃任务列表绑定、防自改扩权与任务池校验（`--require-task-scope` + `--check-task-pool` + [`agents/current_task.json`](current_task.json)）**：
   - [`agents/current_task.json`](current_task.json)（`schema_version: "2.0"`）维护当前活跃任务列表（`active_tasks`），每项记录 `task_id`、`owner`、`expected_line`、`allowed_prefixes`、可选的 `forbidden_prefixes`（如允许 `code/` 但禁止修改 `code/a1_train/`）及可选的 `pool_path`（指向 [`agents/task_pools/<TASK-ID>.json`](task_pools/)）。
   - 单次业务 commit 只要其全部改动路径（含新增、修改、删除及重命名源/目标）完整落在列表内**至少一个活跃任务**的允许范围内（且未触碰该任务的 `forbidden_prefixes`），即予放行，支持 SemEval 与学习线并行推进。
   - **任务绑定文件单独提交与父 commit 校验**：`agents/current_task.json` 的修改**必须单独作为一个 commit 提交**（禁止与任何业务代码或文档混在同一个 commit）；检查器扫描任意非绑定 commit `C`（含合并提交相对第一父提交 `C^1` 的净改动）时，强制读取其**父 commit `C^`** 中的 `agents/current_task.json`（扫描未提交改动时读取 `HEAD` 的绑定），杜绝同一 commit 一边篡改 `current_task.json` 一边越界改其他工作线的漏洞，并对不带尾部斜杠的目录前缀（如 `.../论文研究`）做精确目录归类防护。
   - **任务级分端信息共享池校验（`--check-task-pool`）**：在 `--require-task-scope` 或 `--check-task-pool` 下自动核验 `agents/task_pools/*.json` 的分端状态、`task_id / expected_line / allowed_prefixes` 与 `current_task.json` 一致性，及 `github_repo: "synced"` 产物的仓库跟踪完整性（拦截只交 `README.md` 而漏交 `.gitignore` 忽略的数据文件的假同步）。
2. **公开发布门禁覆盖全部扫描模式（`--require-public-ready`）**：
   - 在 `--files`（即使同时传入 `--task-manifest`）、commit 范围扫描与暂存区/工作区扫描中同步执行：凡带有 `可见范围: 工作区私有` 或 `当前状态: 待审/退回/待提稿` 的文件均报错拦截。
   - 发布前检查位置：从 Drive 导出文件至公开仓库 `study_note` 时，**在本地提交/推送前**运行检查。由于 `.git/hooks/pre-push` 仅保存在当前本地 clone（不随 Git 仓库克隆自动分发，临时 VM 重建后也会清空），**每个会执行 `git push` 的 clone（含 Antigravity 各对话、Codex 及本机 clone）在首次推送前均须先运行一次 `python3 agents/check_repo_hygiene.py --repo . --install-pre-push-hook` 安装本地钩子**（钩子执行 `--ownership-mode error --require-task-scope --require-public-ready`）；GitHub Actions 作为远端补充复核（追加 `--check-task-pool`）；首次推送新分支（远端 SHA 为全零 `0000...`）时扫描全部将被发布的可达历史，不退化为只检查最后一个 commit（注：针对尚未引入 `agents/current_task.json` 的 `2a465953` 之前早期根历史，新分支不得直接以 `--require-task-scope` 从根历史全量首推，正常增量工作在已有远端历史基准的 `note` 分支上提交推送）。
3. **非空双向回执校验（`--verify-receipt`）**：
   - `verify_bound_receipt` 拒绝空输入 `{}`，强制要求传入 `--files` 读取待审文件的实际字节并双向核对回执中的 `file_hashes` 清单（用于 Drive 交接稿与导出文件校验）。

### 3.2 把审查限定在本次产物及受影响的地方

1. **写作者前置自检与独立子 agent 自审**：交接前先完成已有脚本检查，并在 Drive 任务目录附上与当前文件 `SHA-256` 绑定的检查回执（注：自动检查通过仅代表格式/隐私/范围合规，不代表学科内容已审核通过）；向 `Pan-Yan-0` 或其他端交付跨端提示、任务入口或交接包前，须先经只读独立审查子 agent 逐项核对仓库与 Drive 真相源。
2. **审阅者聚焦四类实质问题**：只检查会改变**正确性、结论、可运行性和隐私边界**的问题：
   - **SemEval 实验线重点**：`fold` 隔离、标签方向（`F`/`B`）、对照条件、指标定义和运行回执。
   - **NLP 学习笔记与论文阅读重点**：概念定义、公式推导、张量形状（tensor shape）及具体例子。
   - **多模态试验产物重点**：图表数字、公式和模型结构仍由原始数据或代码核对。

## 4. 错误分级与四档修法

每被纠正一次，按顺序选修法，前一档做不到才选下一档并写明原因：
1. **改结构**：让错误没机会发生（例：Drive 作为唯一共同读写入口；仓库 `agents/current_task.json` 绑定当前任务范围；回执绑定文件实际字节 `SHA-256` 快照；发布前本地门禁先于 `git push` 执行）。
2. **自动检查**：活干完自动过一遍，犯了马上拦下（例：`check_archive.py`、`check_drafts.py`、`agents/check_repo_hygiene.py` 及 GitHub Actions `repo-hygiene.yml`）。
3. **写成规矩**：前两档做不到时才加；一条规矩被违反一次即升为“中度”，必须改成第 1 或第 2 档。
4. **Pan-Yan-0 抽查**：只留给硬规则与每周抽查清单，不作为修法。

| 级别 | 判定标准 | 处理步骤 |
|---|---|---|
| **轻** | 被已有自动检查拦下；或只影响单个未交接的文件 | 当场改，不记台账 |
| **中** | 越过了本该拦住它的环节，到了另一端或 Pan-Yan-0 手里；或同类错第二次出现；或别人已基于错误状态干活 | 止损 → 找本该拦住它的那一层 → 用第 1 或第 2 档修 → 注入错误做回归测试 → 记进 [纠错台账](纠错台账.md) |
| **重** | 进了给导师看的结论；隐私进了公开仓库；造成数据、算力或已发布帖子的不可逆损失 | 停掉这条线 → 回滚 → 改结构 → 回归测试 → 同步所有端 → 再恢复 |

历史纠错记录与扫描验收回执统一在 [纠错台账](纠错台账.md) 单点维护，不在本文重复抄写。
