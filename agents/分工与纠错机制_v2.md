## 2. Google Drive 主工作区与 GitHub 同步架构

**核心原则（Pan-Yan-0 已定）**：以 **Google Drive（`Pan-Yan-0_工作区`）作为所有端共同读写的主工作区**，**GitHub 保存同步副本、运行 Actions 自动检查并保留版本历史**。

| 内容类别 | Google Drive（所有端共同读写主工作区） | GitHub（同步副本、Actions 检查与版本历史） |
|---|---|---|
| **分工、各线状态、学习存档** | 当前权威版本，各端从这里开工 | 同步到对应公开（`study_note`）或私有仓库（`personal_study_image`） |
| **NLP 论文、素材、图片、音频、视频** | 原文件和正式产物统一保存 | 保存需要版本管理的文字、索引和引用 |
| **SemEval 代码、配置、运行包** | 保存对应版本，供各端读取和交接 | 同版本代码用于 `diff`、测试和 Actions |
| **权重、逐条预测、结果 ZIP** | 完整保存，附 `SHA-256` 哈希 | 保存指标摘要、清单和哈希 |
| **审阅意见、自动检查回执** | 写回对应任务目录，所有端可读 | 保存运行记录与必要的审计证据 |

### 2.1 可见范围隔离与文件管理 6 项必要信息

1. **Drive 内两级可见状态**：
   - **`工作区私有`（默认）**：所有新草稿、私有记录、个人画像、中间讨论默认处于该状态，只留在 Drive 私有工作区或同步至私有仓库。
   - **`允许公开发布`**：拟进入公开仓库 `study_note` 的笔记、实验文档与代码，必须经过 `agents/check_repo_hygiene.py --require-public-ready` 自动检查与对应审阅通过后方可标记并发布。
2. **交接与任务文件固定记录 6 项必要信息**（由 `agents/check_repo_hygiene.py --require-handoff-header` 自动校验）：
   - `任务与当前负责人`（如 `TASK-LEARN-001 | Gemini 网页端`）
   - `允许修改范围`（如 `ML_note/原理笔记/`、`ML_note/实验/ShortGPT_BI删层/`）
   - `来源版本`（记录源 Git commit、Drive `fileId` 与输入内容 `SHA-256`）
   - `可见范围`（`工作区私有` 或 `允许公开发布`）
   - `当前状态`（`待提稿` / `待审` / `退回` / `通过`）
   - `正式结果链接`（及拟合入仓库的 `目标仓库路径`；正式文件原位更新保留同一链接，旧交接稿移入归档目录，统一入口只指向当前版本；更新 Drive 副本前核对源 commit 与内容哈希，避免两边各自修改后互相覆盖）。

### 2.2 互通与防覆盖的三步闭环同步

1. **统一入口读取**：各端先从 Drive 的统一入口（`00_入口/当前任务与交接入口.md`）读取当前任务。入口指向具体文件，文件头注明负责人、允许修改范围、版本和状态；Gemini 提交新稿后，其他端可直接读取。
2. **确定版本送检**：Antigravity 基建把 Drive 上的确定版本拉取到本地/GitHub 检查，记录 **Drive 文件 ID、内容 `SHA-256` 哈希和基线 Git commit** 的对应关系；`agents/check_repo_hygiene.py`（及 GitHub Actions）检查这份确定的快照。
3. **版本绑定回执写回 Drive**：自动检查生成的回执（`CHECK_RECEIPT_<任务ID>.md` 与 `.json`）写回 Drive 对应任务目录，**回执显式绑定被检查版本的 `SHA-256`**。若写作者（如 Gemini）在检查或审阅期间又改了文件，`--verify-receipt` 会因哈希不匹配直接报“版本失效”，旧版本的“通过”只适用于旧版本，新稿继续处于`待审`状态。

### 3.1 把“任务允许改哪里”交给检查脚本（`agents/check_repo_hygiene.py`）

- 除拦截“同一 commit 混改多个工作线”外，`agents/check_repo_hygiene.py` 新增 `--expected-line`、`--allowed-prefixes` 与 `--task-manifest` 参数，直接读取交接文件中的`允许修改范围`对照实际 `diff`（含新增、修改、删除 `D` 和重命名 `R` 的两端）。
- **防单线越界**：例如 B1 推理包任务允许修改 `ML_note/实验/SemEval_DiCo-NLI/code/` 与对应文档，若某次提交只修改了 `ML_note/原理笔记/` 或 `论文研究/`（虽未混改多条线，但越出了 B1 任务允许范围），检查器立即报错拦截（`越界修改`）。
- **防父目录前缀穿透**：即使允许前缀写为 `ML_note/实验/SemEval_DiCo-NLI/`，若未显式声明 `论文研究/`，脚本自动拒绝修改属于独立工作线的 `ML_note/实验/SemEval_DiCo-NLI/论文研究/`。

### 3.2 把审查限定在本次产物及受影响的地方

1. **写作者前置自检**：交接前先完成已有脚本检查，并在 Drive 任务目录附上与当前文件 `SHA-256` 绑定的检查回执。
2. **审阅者聚焦四类实质问题**：只检查会改变**正确性、结论、可运行性和隐私边界**的问题：
   - **SemEval 实验线重点**：`fold` 隔离、标签方向（`F`/`B`）、对照条件、指标定义和运行回执。
   - **NLP 学习笔记与论文阅读重点**：概念定义、公式推导、张量形状（tensor shape）及具体例子。
   - **多模态试验产物重点**：图表数字、公式和模型结构仍由原始数据或代码核对。
3. **复验与收敛边界**：修订后只复验原问题及受影响的部分，通过即结束；文字润色仅作为可选建议，不阻塞通过；新实验、新功能另立新任务。

### 3.3 SemEval 与创作线具体衔接

1. **SemEval 线**：
   - 代码编辑可在本地 Git 工作区完成，交接时将代码包、版本记录与检查回执同步发布到 Drive `10_交接/SemEval/`（或 `20_实验包/`），使审阅者与运行者拿到同一份确定快照。

   - **B1 推理包、PiSSA 包及后续新包**：Antigravity「SemEval 对话」任实现负责人，Codex 任独立审阅人；开跑前可将冻结协议放进 Drive 由 Gemini 做补充跑前协议审查。

### 3.4 首阶段小闭环试跑（NLP 笔记 Drive 交接闭环）

在扩展到实验包和多模态素材前，先跑通以下四步最小闭环：

## 4. 错误分级与四档修法

每被纠正一次，按顺序选修法，前一档做不到才选下一档并写明原因：
1. **改结构**：让错误没机会发生（例：Drive 作为唯一共同读写入口；状态只写一处；回执绑定文件 `SHA-256` 快照；公开与私有状态显式隔离）。
2. **自动检查**：活干完自动过一遍，犯了马上拦下（例：`check_archive.py`、`check_drafts.py`、`agents/check_repo_hygiene.py` 及 GitHub Actions `repo-hygiene.yml`）。
3. **写成规矩**：前两档做不到时才加；一条规矩被违反一次即升为“中度”，必须改成第 1 或第 2 档。
4. **Pan-Yan-0 抽查**：只留给硬规则与每周抽查清单，不作为修法。

| 级别 | 判定标准 | 处理步骤 |
|---|---|---|
| **轻** | 被已有自动检查拦下；或只影响单个未交接的文件 | 当场改，不记台账 |
| **中** | 越过了本该拦住它的环节，到了另一端或 Pan-Yan-0 手里；或同类错第二次出现；或别人已基于错误状态干活 | 止损 → 找本该拦住它的那一层 → 用第 1 或第 2 档修 → 注入错误做回归测试 → 记进 [纠错台账](纠错台账.md) |
| **重** | 进了给导师看的结论；隐私进了公开仓库；造成数据、算力或已发布帖子的不可逆损失 | 停掉这条线 → 回滚 → 改结构 → 回归测试 → 同步所有端 → 再恢复 |

历史纠错记录与扫描验收回执统一在 [纠错台账](纠错台账.md) 单点维护，不在本文重复抄写。
