# v3.1 · Kaggle 运行说明（DeBERTa 为问题二最终模型，问题三专项模型）

## 这一版改了什么

依据题面原文和 v3 全量结果，改动如下：

| 改动 | 做法 | 为什么 |
|---|---|---|
| 输入接口统一 | DeBERTa 的文本只从 `text_bert` 还原，不再读 `raw_text` | 附件3 没有 `raw_text`；题面要求训练、验证、专项测试“同一输入接口”，并把 `raw_text` 定义为“用于阅读核查，非数值特征” |
| 可提交 | 问题二只部署单个模型（fp16 约 15 MB）。候选有两个：事先定好的种子 17，或 5 种子集成蒸馏出的学生 `deb_kd`。规则见下方协议 | 附件总计 ≤ 50 MB，问题一已占约 16 MB；5 种子集成 fp16 要 73 MB，交不上去 |
| 输出一律满足题面定义 | 负向强度 < 0，中性强度 = 0，正向强度 > 0，一律强制执行；报告同时给出原始输出的指标 | v3 附件3 出现了“负向却给正强度”“中性强度不为 0” |
| 选 epoch 更稳 | LoRA 与头部权重做指数滑动平均（0.998，warmup 之后开始），8 个 epoch | v3 相邻 epoch 在 VS 上能差 ±3 个 F1 点 |
| 问题三专项模型 | 共享问题二的编码器（冻结），加一个模态可加分解融合头（约 0.7M 参数，fp16 约 1.3 MB）。训练用完整输入和局部缺失视图，再做 8 子集整路丢弃。文本证据改为逐个整词遮挡 | 题面要求“两类专项模型”；每个模态的贡献可以直接从结构读出，再用精确 Shapley 核对；整词遮挡不会把虚词混进证据 |
| 朴素零填充对照 `naive` | 与 base 同结构、同种子（3 个）。缺失位置当作“原始零值”参与池化，没有任何缺失感知 | 回应题面“常规固定权重融合……性能急剧下降”，量化掩码池化本身的作用 |
| 面板指标 | 新增稳定性（相对完整输入的类别翻转率、强度变化 \|Δŷ\|）、按绝对缺失位置数分组（1–2 / 3–5 / 6–10 / 11–20 / >20）、加权 F1 | 题面强调“稳定输出”和“缺失时长”，F1 没写平均方式 |
| 提交与合规 | 自动生成 `submission/`：fp16 参数、配置、附件3/4 结果、关键帧，附体积核对和 fp16 往返核对；日志与表格去掉输入路径里的账号名 | 50 MB 限制；提交材料不得出现身份信息 |

**预期：** DeBERTa-v3 区分大小写，改用小写的还原文本会损失一点信息，所以 v3.1 的 DeBERTa 可能比 v3 略低。这是统一输入接口的代价，EMA 和集成蒸馏用来弥补一部分。

## 事先锁定的协议（训练前写入 `PROTOCOL_v31.json`）

- **验证集切分：** 按源视频对半分为 VS 和 VC，与 v3 完全相同。
  - VS 用来选 epoch、拟合规则层、选部署模型。
  - VC 对 DeBERTa、蒸馏学生和问题三融合头是没有碰过的留出数据。
  - base 和 naive 沿用 v1 的做法，在整个验证集上选 epoch，所以 VC 对它们不算留出。
- **部署规则：** 只在“能放进附件”的两个候选里选，比较 VS 上按视频 5 折的折外 J（含规则层）。
  - 学生至少高出 0.003 才部署学生，否则部署更简单的种子 17。
  - 集成只作参考上限。
  - 候选都失败时，只在 deb / deb_kd / base 中退回，朴素对照不参与。
- **测试集：** 只在所有选择完成后评估一次。

## 怎么跑

1. **导入与设置：** Kaggle → Import Notebook，选 `gmcm_v31_kaggle.ipynb`；GPU 选 T4，**打开 Internet**（下载 DeBERTa-v3-large 和 MMS 对齐模型）。
2. **Add Input：**
   - 比赛数据集；
   - 检查点数据集 `some-pt`（只用到 `base_s*.pt` 和 `train_config.json`）。

   v3 的 DeBERTa 检查点即使加进来也会被自动跳过（它们用 `raw_text` 训练，文本来源不同）。
3. **Q3-02 的修订量（可选）：** 在配置单元 `ATT4_MANUAL` 里 sample="02" 那一行填：
   - `shift_s`：正数推后，负数提前；
   - `evidence`：`"T"` / `"A"` / `"V"` / `"all"`。

   不填也能跑，状态会标为 `revised_pending`。
4. **冒烟测试：** 第一行改成 `SMOKE = True`，Run All，约 20 分钟。会用 1 个 epoch 重训所有模型（含蒸馏学生），结果在 `outputs_v31_smoke`。日志里重点看：
   - `DeBERTa 词元映射：`
     - `source` 应为 `text_bert`，`raw_aligned` 为 0，`detok` 等于样本数；
     - `bert_pos_without_token` 接近 0（只有超长句被截断时才有）。
   - `LoRA 模块 144 个`。
   - `朴素零填充的“原始零值”`：`clipped_a` / `clipped_v` 一般为 0。
   - `部署选择（v3.1）`，以及 `问题三融合头：选中 epoch …`。
   - `提交文件夹：` 里 `fp16_check` 的 `q2_class_agree` 应为 1.0 或非常接近。
   - 最后出现 `v3.1 全部完成`。
5. **全量运行：** 改回 `SMOKE = False`，预计 3.5–4 小时，建议用 Save & Run All（Commit）在后台跑。各阶段约为：

   | 阶段 | 用时 |
   |---|---|
   | naive 3 个种子 | 17 分钟 |
   | DeBERTa 5 个种子 | 65 分钟 |
   | 蒸馏学生 | 15 分钟 |
   | 全部评估 | 75 分钟 |
   | 扩展扫描 | 25 分钟 |
   | 问题三与附件 | 15 分钟 |
6. **取结果：**
   - 下载 `/kaggle/working/outputs_v31.zip` 发回，`submission` 文件夹也在里面。
   - `outputs_v31_ckpt.zip` 里是新训的检查点（naive 3 个、DeBERTa 5 个、蒸馏学生 1 个，约 180 MB）。建议也下载，以后作为数据集上传（**保留文件夹结构**，每个文件夹里的 `train_config*.json` 用来核对配置），重跑时就能跳过约 2 小时的训练。

## 看结果时重点看这几处（`REPORT_v31.md`）

- **第 1 节 目标达成：**
  - valid（题面“基础性能评价”的口径）、VC（留出）、test 三套，都是规则层 + 一致化之后的结果；
  - 带“（部署）”的那行是实际提交的模型，附按视频的 95% 区间；
  - `incoherent_rules` 应全为 0。
- **第 2 节 部署选择：** 两个候选的 J、选择理由。
- **第 3 节 蒸馏：** `mean_max_prob` 看教师在训练集上的软标签是否接近 one-hot；接近的话，蒸馏的收益会有限。
- **第 4 节 配置汇总：** naive 与 base 的完整输入指标应相近，差别主要在缺失面板和翻转率上。
- **第 7、8 节：** naive − base 的扩展扫描差值，以及按绝对缺失长度的分组。这两节是“常规固定融合在缺失下退化”的直接证据。
- **第 10 节 问题三：**
  - 专项模型与问题二部署模型同表对照；
  - 可加贡献与精确 Shapley 的主导模态一致率；
  - 整词遮挡的删除检验。
- **第 12、13 节：** 附件3/4 的 `n_incoherent` 应为 0。
- **第 14 节 提交文件夹：**
  - 合计应 ≤ 34 MB；
  - fp16 往返核对：`q2_class_agree`、`q3_class_agree` 应为 1.0 或极接近。

## 如果出问题

各步骤失败时会自动降级，原因都记在报告第 16 节：

| 失败情况 | 自动处理 |
|---|---|
| 某个 DeBERTa 种子失败 | 跳过这个种子 |
| 蒸馏失败 | 部署种子 17 |
| 问题三融合头训练或推理失败 | 改用问题二模型解释 |
| DeBERTa 整体失败 | 退回 base，BERT 部分照常出结果 |

需要手动调整的情况：

- **显存不足：** `DEB_BS` 改为 8，或 `RDROP_ALPHA` 设为 0。
- **非有限损失：** `DEB_LR_LORA` 改为 1e-4 再跑，已训完的种子会自动读取。
- **时间紧：**
  - `RUN_KD=False`，省约 15 分钟，部署种子 17；
  - `EXT_SPLITS=["valid"]`，省约 12 分钟，扩展扫描只做验证集。
